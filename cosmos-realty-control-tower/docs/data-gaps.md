# Пробелы данных перед построением дашбордов

## Можно считать уже сейчас

Это безопасные показатели-срезы; они не требуют выдумывать отсутствующую
историю.

### 10 показателей для РОПа

1. Количество новых лидов по `DATE_CREATE`.
2. Текущий объём лидов по статусам.
3. Текущий объём сделок по стадиям основной воронки `CATEGORY_ID=0`.
4. Лиды и сделки по ответственному брокеру `ASSIGNED_BY_ID`.
5. Лиды и сделки по отделу через `UF_DEPARTMENT`.
6. Количество открытых и выполненных CRM-активностей по `COMPLETED`.
7. Просроченные активности по `DEADLINE`.
8. Текущие показы: назначенные и проведённые — раздельно, без двойного счёта.
9. Текущие брони по способу оплаты: наличные или ипотека.
10. Успешные и потерянные сделки по текущей стадии.

Перед эксплуатацией для пунктов 8–10 нужно утвердить, считать лиды или сделки
главным источником. Сам расчёт возможен уже сейчас.

### 10 показателей для собственника

1. Входящие лиды по дням/неделям/месяцам.
2. Распределение лидов по 18 источникам.
3. Распределение лидов и сделок по UTM-кампаниям при заполненных UTM.
4. Текущий портфель сделок основной воронки по стадиям.
5. Текущие брони: всего, наличные, ипотека.
6. Количество сделок на регистрации.
7. Количество сделок со статусом «Оплачено клиентом».
8. Количество сделок, где счёт на комиссию выставлен.
9. Количество сделок в состоянии «Комиссия получена» — без суммы денег.
10. Успешные и потерянные сделки по брокерам и отделам.

Это операционные количества. Выручку, скорость прохождения воронки и честную
конверсию за период пока считать нельзя.

## Можно считать после настройки

| Показатель | Что мешает | Минимальная настройка |
| --- | --- | --- |
| Время до первого звонка | Не подтверждены типы и провайдеры звонка | Утвердить справочник активности и первый фактический звонок |
| Доля конструктивных диалогов | Нет единого бизнес-признака | Формализовать критерий и сохранять результат |
| Конверсия между этапами за период | Нет доступной истории переходов | Дать read-only доступ к `crm.stagehistory.list`, BI-набору или вести журнал новых переходов |
| Время на каждой стадии | Нет `CREATED_TIME` перехода | Тот же журнал истории |
| Назначено → состоялось для встреч | `COMPLETED` не доказывает участие клиента | Тип встречи плюс обязательный результат |
| Назначено → проведено для показов | Этап есть в лиде и сделке, нет единого источника | Утвердить объект учёта и фактическую дату |
| Конверсия показ → бронь | Нет истории и возможен двойной счёт | История + единый источник |
| Конверсия бронь → сделка | Нет истории/правила отмены | Даты брони, отмены и успешного завершения |
| SLA брокеров и РОПов | Не завершена карта ролей | Заполнить `UF_HEAD`, список отделов продаж и нормативы |
| Эффективность рекламных кампаний | Неполные UTM и нет расходов | Контроль UTM, перенос лид → сделка, импорт рекламных затрат |
| Сумма ожидаемой комиссии | Поле суммы не идентифицировано | Обязательное поле суммы и валюты |
| План-факт комиссии | Нет плана и факта дат/сумм | Плановая и фактическая сумма/дата оплаты |

## Невозможно считать без доработки CRM

- выручку и маржу по комиссиям: найден статус получения, но не подтверждено поле
  фактической суммы комиссии;
- точное время входа в каждую стадию: текущий webhook не предоставляет
  `crm.stagehistory.list`, а `DATE_MODIFY` использовать нельзя;
- факт конструктивного диалога: нет утверждённого измеримого результата;
- факт состоявшейся видеовстречи: текущий статус не разделяет назначение и факт;
- причины отмены показа или брони: обязательный классификатор не найден;
- сквозную конверсию «клиент → лид → сделка»: схема контакта/компании и правила
  дублей сознательно не исследовались в этом безопасном этапе;
- ROMI/стоимость лида: в CRM нет проверенных рекламных расходов;
- личную эффективность РОПа для всех отделов: руководитель заполнен только у 8
  из 13 подразделений и не утверждён список отделов продаж.

## Поля и настройки для согласования

Ничего из перечисленного в Bitrix24 не создавалось. Предлагаемый минимальный
набор:

1. `Факт конструктивного диалога` — да/нет, дата, критерий.
2. `Тип встречи` — видео/офлайн/телефон; плановая дата; фактическая дата;
   результат состоялась/не состоялась/перенесена.
3. `Показ` — плановая дата, фактическая дата, результат, причина отмены.
4. `Бронь` — дата, объект, тип оплаты, сумма задатка, дата/причина отмены.
5. `Комиссия` — плановая сумма, фактическая сумма, валюта, дата счёта, плановая
   и фактическая даты поступления.
6. Обязательный `Источник` и правила заполнения/переноса всех `UTM_*`.
7. Обязательный руководитель `UF_HEAD` для каждого отдела продаж.
8. Единый справочник причин потери и обязательность причины.
9. Единый источник истины для показов, броней, оплат и комиссий: лид либо сделка.
10. Read-only источник истории стадий или отдельный журнал новых переходов.

## Следующий этап разработки

Не дашборд. Сначала владелец бизнеса и РОП утверждают:

1. основную воронку и исключение учебных категорий;
2. единый источник каждого события;
3. определения «конструктивный диалог», «встреча состоялась», «показ проведён»;
4. финансовые поля комиссии;
5. структуру отдел → РОП и нормативы времени.

После этого следует отдельный read-only этап: проверить историю стадий и
заполненность на агрегатах без персональных данных, реализовать валидаторы
качества и только затем собрать MVP дашборда РОПа.
